AN INTERACTIVE GUIDE

How does a repository learn to be a roboticist?

A robot drops an object. The useful lesson might be a better grasp, a corrected coordinate transform, or a new verification step. RHO turns that experience into edits to a reusable policy repository.

HELIX is the reflective evolutionary optimizer used in RHO. Follow the mechanism below: what changes, how feedback guides an edit, and how specialists contribute to future improvements.

01
RHO · search space

The candidate is an entire repository.

Reflective optimization can improve code, prompts, or other artifacts using execution feedback. RHO makes a multi-file repository the policy artifact: a Repository-as-Policy (RaP). One mutation can change several cooperating modules.

Route the instruction

The public entry point connects a task instruction to reusable behavior.

Observe→Decide→Act

A change to a pose convention can require matching edits in perception, motion, and outcome checks. The search unit must accommodate that coordination.

Seed, evaluator, and optimization variable

The artifact defines what can be learned. A prompt-only artifact permits prompt edits; a repository permits new control logic, interfaces, and reusable helpers. The seed’s structure is therefore an inductive bias: it can make useful edits easier or encourage repeated monolithic rewrites. HELIX changes the artifact through source edits while keeping the underlying model’s weights fixed.

Start with a seed repository that exposes the required invocation signature, such as run(ctx). A skeleton supplies the initial interfaces and file structure. The user supplies an evaluator that maps a repository and task instance to a scalar score and structured side information.

E(R, τ) = (sτ(R), zτ(R))

Here τ identifies a task, trial, and seed; s is the benchmark score and z carries diagnostics. The scalar score can be a rich shaped reward that credits partial progress or binary task success (0 for failure, 1 for success). In our CaP-Bench experiments, s ∈ [0, 1] is the environment’s final shaped reward. HELIX imposes no language constraint on repositories beyond what the target runtime accepts.

02
HELIX · parent and minibatch

Choose what to improve and where to test it.

The seed is evaluated to initialize the frontier. After that, HELIX samples a parent from candidates that preserve useful strengths on the chosen frontier. A candidate’s chance of being selected is proportional to its best-key coverage after pruning. We will build this frontier explicitly in step 5.

Next, sample a small training minibatch. RHO adds stratified batch sampling: choose task families, then sample trials or seeds within those families. This gives task families a share of each batch even when their trial counts differ. Increase the number of groups to broaden task coverage; increase examples per group to expose variation across seeds. Both increase the amount of feedback and evaluation work.

Sampling and skip details

HELIX’s standard epoch-shuffled sampler visits shuffled training examples. RHO’s stratified sampler shuffles within groups and interleaves task families, with configurable numbers of groups and examples per group. If too few groups exist, the implementation falls back to epoch-shuffled sampling. The canonical Robosuite configuration uses a minibatch of two.

Evaluate the parent and collect its traces before asking for a mutation. If every sampled score already reaches the configured perfect-score threshold, the perfect-batch rule can skip that mutation attempt. This skip decision applies to the sampled instances.

Search intuition

More generations and broader evaluation both take time.

Generation count and minibatch size are independent settings. You can run many generations with a large minibatch; doing so requires more evaluation work and usually more wall-clock time.

Batch size also changes the agent’s attention. More groups expose different task families; more seeds reveal variation within a family. More examples can reveal regressions, but can also make the reflection prompt longer and the requested improvement less focused.

03
RHO · tool-enabled mutation + REaaS

One mutation is a development session.

HELIX uses natural-language reflection on successes, failures, and execution traces to guide a tool-enabled coding agent working across the repository.

The agent can inspect files, edit modules, write temporary tests, execute candidate policies, read tracebacks, and revise again before submitting one child. Robot-environments-as-a-service (REaaS) provides the allowed environment calls. We use Robosuite, LIBERO, and RAI; the interface can expose other benchmarks.

The evaluator returns one scalar per instance: a shaped reward that credits progress, or binary task success (0 or 1). HELIX compares the summed scores on the paired minibatch to decide acceptance.

Execution traces, errors, stdout/stderr, visual-difference summaries, and optional judge diagnostics help explain behavior.

The scalar says how the rollout scored. Actionable Side Information (ASI) supplies evidence for what to change. Reflection uses that evidence to propose a targeted repair.

What goes into reflection?

Instrumentation is part of the learning interface. A bare failure score hides where execution went wrong; a useful log can expose a failed precondition, a pose mismatch, or a premature release. Useful diagnostics distinguish plausible causes and suggest a testable next edit. Successful traces also matter because they show behavior worth preserving.

The mutation session receives the parent repository, its full evaluator output for the current batch, task instructions, and domain context. The prompt asks the agent to improve weaknesses while preserving strengths. Structured side information is supplied by the evaluator; available fields depend on the benchmark.

In the CaP-Bench setup, optional judge axes describe uncertainty management, contingency handling, strategic coherence, physical grounding, and adaptive exploration. These axes and visual-difference summaries guide the agent’s diagnosis. Acceptance uses the scalar environment reward. Timing and token-cost streams are withheld from the reflection prompt in the reported setup. Each session has a bounded tool/turn budget and ends by submitting a candidate snapshot.

HELIX gate RHO · optional staged validation

A promising edit must earn more evaluation.

Run the child on the same training minibatch as its parent. The default gate requires a strict increase in total reward. An improvement on one instance may offset a regression on another. Some RHO experiments allow equality to admit more candidate diversity.

The child passes both gates and proceeds to full validation. Frontier retention is a separate decision.

Σ sτ(child) > Σ sτ(parent), for τ ∈ B

Staged validation is RHO’s additional filter. Before paying for the full validation set, compare the child and parent on a smaller validation subset using the configured acceptance criterion. This gate is enabled in our LIBERO runs and disabled in the canonical Robosuite run.

Gate outcomes, cost, and stopping

The parent remains available when a child is rejected. Passing the training gate (or both gates when staging is enabled) only promotes the child to full validation. Full per-instance scores determine frontier retention.

The current staged implementation uses a configured prefix of validation instance IDs and the parent’s stored scores on those same IDs. It applies the stage only when the needed parent scores exist. Previously evaluated instances can be reused through the evaluation cache; this reduces repeated evaluation work.

Search repeats until its configured budget or stopping condition is reached. An attempt can end in a failed mutation, a rejected proposal, a perfect-batch skip, or a retained candidate.

05
HELIX · coverage, pruning, and selection

Keep useful specialists available for the next mutation.

The frontier itself is a design choice in HELIX. We use an instance frontier in Robosuite and an objective frontier in LIBERO. The first tracks the best score for each validation instance; the second tracks each evaluator-defined objective’s mean across validation instances. A lower-average specialist can remain a useful parent under either choice.

The candidate archive and the active parent frontier are also different sizes. A larger frontier spreads parent-selection probability across more alternatives; whether that breadth helps depends on their usefulness and the remaining search budget.

Exact coverage rule and ties

For each active frontier key, maintain the set of candidates achieving its best observed score. An instance key refers to one validation example. An objective key refers to one evaluator-provided objective aggregated as a mean over validation examples. The four objective labels are chosen for this teaching example. Collect candidates appearing in any best set. Examine them in ascending aggregate-score order. Remove a candidate if every best key it covers is also covered by another remaining candidate; restart the scan after each removal until no further removal is possible.

Coverage can be redundant across several other candidates. A candidate tied for a best score can be removed when the remaining candidates cover all its best keys.

P(parent = R) = c(R) / Σ c(Q)

c(R) counts R’s appearances in the cleaned best-key sets. Coverage counts best keys. A shaped reward below 1 can still be the current best. The interactive table uses the same iterative coverage rule, with synthetic scores. Its scalar mean remains separate from the frontier-key values. The frontier type controls retention and parent sampling. The scalar minibatch gate uses its own acceptance criterion. HELIX also supports hybrid and cartesian key spaces; the two modes shown here are the choices used in these RHO experiments.

06
RHO · isolation boundary

Control access to tools and evaluator files.

A file-editing agent can improve the policy or tamper with what measures it. RHO separates the mutable workspace, the evaluator, and robot services. A sidecar proxies whitelisted REaaS calls; evaluator-owned files stay outside the agent’s workspace, and integrity checks reject modifications to protected artifacts.

Tools available during mutation and deployment

In the CaP-Bench experiments, mutation uses M4-style debugging: the coding agent may run tests, inspect logs, and query visual-difference feedback. Scoring executes the child through the stricter S4 surface: no deployment-time visual-difference feedback, multi-turn corrective editing, or LLM code-generation calls. Evaluator side information is post-hoc, for future mutations.

The boundary excludes evaluator source, benchmark splits, judge prompts, and benchmark metadata from the mutator workspace.

07
Selection RHO · deployment

Many search branches. One evolved RaP.

At the end of the main frontier-based search, select the surviving repository with the highest mean validation reward, with validation coverage breaking ties. That repository is the deployable artifact.

R* = arg maxR ∈ FT (1 / N) Σi=1…N si(R)
WHAT REMAINS AT DEPLOYMENT?
Selected RaP→Python controller→Robot tools

The evolved repository runs as a controller. Its source stays fixed during the scored rollout, and it can call learned perception services through the documented interface.

We deploy the RHO-evolved RaP on real robots and demonstrate sim-to-real transfer across robot embodiments and to unseen objects. The two-robot animation above illustrates this distinction; the hardware experiments provide the evidence.

Experiment-specific selection and what is held out

Improving one demonstration and learning a reusable policy are different goals. Search feedback helps construct the artifact; evaluation on unseen conditions asks whether that artifact generalizes.

The mean-validation frontier rule describes the main search protocol. The RAI portability experiments use a separate best-by-train selection after ten generations, followed by evaluation on a held-out test split. RHO evolves RAI’s prompts and tool-edit module within its existing ROS 2 connector, deployment loop, and inference driver.

Validation guides search; held-out evaluation measures generalization. In the canonical Robosuite configuration, training and validation use the same 70 task/trial IDs; external evaluation spans 700 trials, including 630 not seen during search.

PUT IT TOGETHER

The complete search loop

  1. Evaluate the seed on validation instances and initialize the configured frontier.
  2. Sample a frontier parent, then a training minibatch; evaluate the parent and collect diagnostics.
  3. Skip a perfect minibatch when configured. Otherwise, reflect and run a bounded tool-enabled repository mutation.
  4. Reject edits that violate integrity. Score the child on the same batch and apply the configured reward gate.
  5. If enabled, apply the staged validation gate. Evaluate promoted children on the full validation set.
  6. Update the configured best-key sets, prune redundant coverage, and repeat until the budget ends.
  7. Select one repository for deployment using the experiment’s selection protocol.

HELIX performs reflective evolution, paired comparisons, and coverage-based selection with configurable frontier keys. RHO expands the search artifact, the mutation process, the robot interface, the isolation boundary, and the training/validation schedule.
