Abstract

Code-as-Policies (CaP) has shown that large language models (LLMs) can write code to solve robotics tasks by composing perception, planning, and control primitives. Recent CaP systems, however, rely on multi-turn code-generation loops at test time, which is often infeasible for real-time robot control. We introduce Robotics Harness Optimization (RHO), a novel paradigm in which tool-enabled coding agents, at training time, propose and search for interpretable neurosymbolic multi-file policy repositories (Repositories-as-Policies) that compose these primitives rather than a single prompt, function, or file. RHO searches with reflective feedback from environment reward and execution rather than demonstrations. We show that our method generalizes to perturbed pick-and-place settings like LIBERO-PRO, reaching 64.33% success rate while CaP-Agent0, the prior leader, reaches 18.03% over the same primitive API, and VLAs trained from demonstrations, π₀.₅ and OpenVLA, achieve an average 13.20% and 0.0% success rate respectively. Under single-turn evaluations on Robosuite, RHO reaches 70.0% at 9.31 s per trial, exceeding the 68.29% prior record that required up to 6 turns of corrective LLM code edits and 113.6 s per trial, a 12.20× speedup. We further show that the RHO evolved repository also deploys unchanged to a different robot from that in simulation and successfully picks up objects never seen during training in 17 of 20 real trials. When an LLM is used in the control loop, as on RAI’s hard O3DE benchmark, RHO optimizes the deployed agent’s multi-file harness of prompts, tools, and control code, improving held-out success from 23.5% to 44.3% with 20% less wall-clock time and 27% fewer tool calls. Videos and further information: https://rho-anon.github.io.

Overview

RHO moves interactive policy development from inference time to training time. A coding agent uses robot execution feedback to develop, test, and refine multi-file repositories before deployment. In CaP-Bench, the selected repository runs as fixed code with no deployment-time LLM code generation.

The complete search loop

RHO combines HELIX, which searches multi-file policy repositories, with Robot Environment as a Service (REaaS), which gives the coding agent access to robot observations and actions through a controlled interface.

Benchmark APIs

CaP-Bench provides robot manipulation tasks in Robosuite and LIBERO. RAI connects an LLM agent to ROS 2 tools in the O3DE simulator. In both settings, a policy observes the scene and acts through the supplied APIs:

CaP-Bench exposes perception, grasp planning, inverse kinematics, and motion as separate calls. In RAI, move_to_point performs a fixed-orientation pick-and-place action using gripper commands and MoveIt motion planning and execution. The O3DE experiments expose the three tools shown above, with fixed names and signatures. RHO searches for repositories that compose the available APIs to maximize the evaluator’s score.

Why search before deployment?

Multi-turn Code-as-Policies systems spend deployment time generating and correcting programs. RHO searches before deployment, preserving useful candidate repositories and refining them with execution feedback. In CaP-Bench it ships fixed policy code; in RAI it ships an improved harness around the existing LLM-driven loop.

Method

From reflective evolution to repository search

RHO follows the reflective evolutionary recipe of GEPA’s optimize_anything: evaluate a candidate, reflect on its successes and failures, propose a child, and retain useful candidates. HELIX changes what the agent can edit and how it makes that edit.

Follow one illustrative child from feedback to independent scoring, then change the validation frontier to see which repositories become future parents.

The candidate is an entire repository.

RHO makes a multi-file repository the policy artifact: a Repository-as-Policy (RaP). One mutation can change several cooperating modules while keeping the underlying model’s weights fixed.

The seed supplies the invocation signature and initial structure. The evaluator maps a repository R and instance τ to a scalar score and structured diagnostics:

E(R, τ) = (sτ(R), zτ(R))

Here τ identifies a task, trial, and seed. Robosuite supplies a shaped reward that can credit partial progress; LIBERO supplies binary task success. Training feedback guides edits, validation guides retention and selection, and held-out conditions evaluate the selected repository after search.

Choose a parent and a training minibatch.

HELIX samples a parent from the frontier, weighted by the validation keys on which it remains best after pruning. RHO adds stratified sampling: choose task families, then trials or seeds within those families. This gives different families a share of the feedback.

A perfect minibatch can be skipped when configured. Broader batches expose more variation; more generations provide more mutation opportunities. Adjust batch size and generations below to explore evaluation work.

How do batch size and generations change the work?

More generations provide more mutation opportunities. A broader batch supplies more feedback by running the parent and child on more instances. Both settings increase the planned evaluation work; trial duration and service time also affect elapsed time.

200 generations × (2 parent + 2 child rollouts) = 800 training rollouts

Assumes full parent and child batches; caching and perfect-batch skips can reduce calls, while debugging and validation add calls.

One mutation is a development session.

HELIX uses reflection on scores and execution feedback to guide a tool-enabled coding agent across the repository. The agent can inspect files, edit modules, write temporary tests, run candidates, read errors, and revise before submitting one child. Robot Environment as a Service (REaaS) supplies permitted environment calls.

Several edits and tool calls can happen inside one evolutionary mutation. Independent evaluation decides whether the resulting child advances.

Reflection receives the parent repository, task context, and evaluator feedback for the current batch. Available diagnostics include execution traces, errors, stdout/stderr, visual-difference summaries, and optional judge axes. They guide the edit; acceptance uses the scalar environment reward. We withhold timing and token-cost streams from reflection in our CaP-Bench experiments.

A promising edit must earn more evaluation.

Run the child on the same training minibatch as its parent. The default gate requires a strict increase in summed reward; some experiments allow equality. Passing this gate earns validation, where frontier retention is decided.

Στ ∈ B sτ(child) > Στ ∈ B sτ(parent)

Keep useful specialists available for the next mutation.

HELIX keeps a frontier of repositories with different strengths. We use an instance frontier in Robosuite and an objective frontier in LIBERO: the first tracks the best score on each validation instance; the second tracks evaluator-defined objective means across validation instances. A lower-average specialist can still be a useful parent.

This is GEPA-style best-key coverage retention. For each key, find the candidates tied for its best observed score. Remove a candidate if other remaining candidates cover all of its best keys; coverage can be supplied by several repositories. In the Add E example, E has a higher mean than A or B, but their combined coverage makes E redundant. Sampling weights count appearances in the cleaned best-key sets:

P(parent = R) = c(R) / ΣQ c(Q)

This example uses Grasp, Lift, Place, and Finish. Our LIBERO frontier tracks the goal, object, and spatial task families. Frontier keys govern retention and parent selection; the training gate uses summed reward.

Separate policy edits from the evaluator.

The HELIX + REaaS architecture separates the editable policy repository from the evaluator. Permitted robot calls cross the sidecar; evaluator source, benchmark splits, judge prompts, and benchmark metadata remain outside the mutation workspace. Protected-file integrity checks reject unauthorized evaluator edits.

The development session can use debugging trials and visual feedback. CaP-Bench scoring runs the submitted child with fixed code and no corrective LLM editing; post-hoc diagnostics can guide a future mutation.

Many search branches. One evolved RaP.

At the end of the main frontier-based search, select the surviving repository with the highest mean validation reward, with validation coverage breaking ties. That repository is the deployable artifact.

R* = arg maxR ∈ FT (1 / N) Σi=1…N si(R)

Evolved cube-lifting policy · Robosuite

RHO engineered its own grasp recovery

RHO’s repository search produced a policy that checks whether a Contact-GraspNet grasp actually lifted the cube and invokes a geometric backup when grasping fails. The evolved backup combines three wrist orientations, two grasp depths, reachability checks, and retries. This recovery runs as ordinary Python at deployment, without another language-model call.

def grasp_single(
    ctx, obj, lift=0.12,
    allow_top_down_fallback=True, prefer_top_down=False,
):
    try:
        ctx['open_gripper']()
    except Exception as exc:
        pass
    # Reachability selection calls plan_world_grasps above.
    chosen = None if prefer_top_down else choose_reachable_grasp(ctx, obj)
    # One simple top-down fallback precedes the task’s retry loop.
    if chosen is None and (allow_top_down_fallback or prefer_top_down):
        pos, quat = top_down_grasp_pose(obj)
    elif chosen is None:
        return None
    else:
        pos, quat, _ = chosen
    hover = pos + np.array([0.0, 0.0, lift], dtype=float)
    if not safe_ik_move_single(ctx, hover, quat, 'single_grasp_hover'):
        return None
    if not safe_ik_move_single(ctx, pos, quat, 'single_grasp_descend'):
        return None
    try:
        ctx['close_gripper']()
    except Exception as exc:
        return None
    if not safe_ik_move_single(ctx, hover, quat, 'single_grasp_lift'):
        return None
    return HeldObject(obj.label, quat, pos, obj.center.copy())

The helper tries one simple top-down pose when no network proposal is reachable. A failed motion returns None; the caller above then starts the backup loop below. An explicitly false lift check triggers the same backup.

Then: three orientations, each at two depths

Three wrist orientations at two depths give up to six top-down attempts. The policy tries each orientation shallow, then deep, skipping unreachable motions and reopening between failures. A lift check that is not false can end the loop early.

RHO searches over policy repositories, leaving the coding agent free to choose how to implement their behavior. Here, search produced a geometric backup with explicit depth offsets, retry ordering, and lift checks. A human can inspect these choices, edit the recovery procedure, and evaluate the modified policy without retraining the underlying models.

How are the depths computed?

The policy segments the cube, deprojects its depth pixels using the camera intrinsics, and transforms those points into world coordinates. cube.center = median(points_world) is the coordinate-wise median of the visible object points. Each backup keeps that center’s x and y, then sets grasp_z = center_z − 0.015 m for the shallow attempt or center_z − 0.030 m for the deep attempt: 1.5 cm or 3 cm downward along world Z.

The offsets are constants in the evolved repository. Both use cube.center from the initial observation; the backup does not recompute that reference between attempts. Lift verification makes fresh observations without replacing it. The hover target is 18 cm above the grasp target, and the requested lift target is 30 cm above it.

How are the orientations defined?

These are fixed wrist orientations in [w, x, y, z] quaternion order. A rotation through angle θ around unit axis u is [cos(θ/2), u · sin(θ/2)]. Here w = 0, so each quaternion encodes a 180° rotation:

The three quaternion constants used by the backup loop
Code constantQuaternion [w, x, y, z]Rotation axis
SINGLE_DOWN_OPEN_X[0, 1/√2, 1/√2, 0]Diagonal between world X and Y
SINGLE_DOWN_OPEN_Y[0, 1, 0, 0]World X
SINGLE_DOWN_OPEN_Z[0, 0, 1, 0]World Y

All three map the wrist’s local Z axis to world −Z. The last two reverse the directed horizontal axes through a 180° turn about world Z. The constant names label stored wrist frames; they do not specify the physical finger axes. Contact-GraspNet supplies the proposals for the initial grasp.

SQRT_HALF = float(np.sqrt(0.5))
SINGLE_DOWN_OPEN_X = np.array([0.0, SQRT_HALF, SQRT_HALF, 0.0], dtype=float)
SINGLE_DOWN_OPEN_Y = np.array([0.0, 1.0, 0.0, 0.0], dtype=float)
SINGLE_DOWN_OPEN_Z = np.array([0.0, 0.0, 1.0, 0.0], dtype=float)


def _lift_cube_top_down(ctx, cube) -> bool:
    try:
        ctx["open_gripper"]()
    except Exception as exc:
        pass
    # Three orientations, each tried at two grasp depths.
    attempts = [
        (SINGLE_DOWN_OPEN_X, -0.015, "down_x_shallow"),
        (SINGLE_DOWN_OPEN_X, -0.030, "down_x_deep"),
        (SINGLE_DOWN_OPEN_Y, -0.015, "down_y_shallow"),
        (SINGLE_DOWN_OPEN_Y, -0.030, "down_y_deep"),
        (SINGLE_DOWN_OPEN_Z, -0.015, "down_z_shallow"),
        (SINGLE_DOWN_OPEN_Z, -0.030, "down_z_deep"),
    ]
    for index, (quat, z_offset, source) in enumerate(attempts):
        grasp = cube.center.astype(float).copy()
        grasp[2] = float(cube.center[2] + z_offset)
        hover = grasp + np.array([0.0, 0.0, 0.18], dtype=float)
        lift = grasp + np.array([0.0, 0.0, 0.30], dtype=float)
        # Skip unreachable approaches before closing the gripper.
        if not safe_ik_move_single(ctx, hover, quat, f"cube_lifting_fallback_hover_{index}"):
            continue
        if not safe_ik_move_single(ctx, grasp, quat, f"cube_lifting_fallback_descend_{index}"):
            continue
        try:
            ctx["close_gripper"]()
        except Exception as exc:
            return False
        if safe_ik_move_single(ctx, lift, quat, f"cube_lifting_fallback_lift_{index}"):
            # Observe the cube after lifting.
            verified = _cube_lift_verified(ctx, cube)
            if verified != False:
                return True
            if index == len(attempts) - 1:
                final_lift = lift.copy()
                final_lift[2] = float(max(final_lift[2] + 0.055, cube.top_z + 0.29))
                safe_ik_move_single(ctx, final_lift, quat, f"cube_lifting_fallback_final_lift_{index}")
                return True
        else:
            # If the full lift is unreachable, try a lower height.
            low_lift = grasp.copy()
            low_lift[2] = max(float(grasp[2] + 0.18), float(cube.top_z + 0.16))
            if safe_ik_move_single(ctx, low_lift, quat, f"cube_lifting_fallback_low_lift_{index}"):
                verified = _cube_lift_verified(ctx, cube)
                if verified != False:
                    return True
        # Reopen before the next orientation/depth attempt.
        try:
            ctx["open_gripper"]()
        except Exception as exc:
            pass
    return False

Excerpts preserve motion calls, thresholds, retry order, and return conditions. Explanatory comments are added; diagnostic logging, planner-output processing, and some annotations are omitted.

The lift check treats occlusion as success and a missing observation as inconclusive. The final top-down attempt makes an extra lift and returns success without another check. If top-down recovery returns false, the caller tries side grasps from four directions.

RAI: optimizing an LLM-driven robot agent

RHO uses GPT-5.5 to evolve RAI’s prompt and tool implementations behind the same ROS 2 interface in O3DE. GPT-5.1 remains the deployed agent. Repository evolution increases held-out mean task score from 68.3% to 88.9% on easy tasks and 23.5% to 44.3% on hard tasks. The prompt-only ablation improves to 79.4% and 37.6%, respectively.

The search ran on cubes. Deployment lifts a computer mouse, absent from simulation.

2

A hand moves the mouse between trials, and once during execution.

Simulation ran on a Franka Panda. These trials run on a Kinova Gen3.

Reading the failure

The arm descends three times onto the spot the mouse left. Grasp synthesis falls back to a path that places the grasp at the median of a segmentation mask’s deprojected depth points, with orientation from a fixed top-down set. Those fall-back attempts stay anchored to the initial observation, so every retry targets a stale pose.

We found this by watching the trial, reading the logs and walking the code. A proposed twelve-line repair refreshes the object observation before a fallback retry, without retraining or new demonstrations. The proposed repair remains untested in these trials.
